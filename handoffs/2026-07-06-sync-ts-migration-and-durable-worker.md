## The migration, in one paragraph

`workers/sync/` is a standalone TS package (own package.json, NOT in the Next build). It wraps every step in **DBOS** (durable execution — checkpoints into our own Supabase Postgres; crash → resume). The dashboard **Run Sync** click writes a `sync_runs` row + POSTs the worker's `/kick`; the worker fetches Gmail (the **Mail Clerk** — one IMAP session → Supabase Storage), then runs 6 report workflows (gsheet first, 4 writers parallel, auditor last), writing progress to `sync_run_events` and results to `sync_runs.result`. The modal subscribes via **Supabase Realtime** — no SSE, no child_process, no laptop dependency. Safety came from a **golden-master parity harness**: the Python is the oracle, every TS port matches its classify output byte-for-byte (`npm run parity`, 12/12). The Python stays in-repo as oracle + manual fallback (Claude Code employees still work) until a future M6.

## Critical learnings (highest value)

- **The command-sandbox cannot open a raw Postgres connection to Supabase:5432** — TCP connects but the DB handshake times out. The SAME creds connect in ~900ms from a normal terminal (Renzo verified). This burned an hour (I wrongly blamed the DB password). **Rule: never test the worker's DBOS/Supabase-DB connection from a Claude Bash tool; it must be tested from Renzo's own Terminal. Gmail (993) and Supabase REST/Storage (443) DO work from the sandbox.** Every worker agent got this warning after the first incident.
- **Wrong-password vs. slow-pooler are indistinguishable by timeout** — a deliberately-wrong password timed out identically to the real one, which PROVED the hang was the sandbox, not the credential. Use that experiment pattern.
- **Banker's rounding** — Python `round()` is round-half-to-even; JS `Math.round` is not. `norm.ts` implements round-half-to-even via decimal-string expansion, `Math.round` is lint-banned in data paths, and the 127 norm fixtures are GENERATED BY RUNNING THE PYTHON. This was risk #1 and the harness caught real drift.
- **Merged-cell trap** — exceljs resolves a merged region's covered cells to the master's value; openpyxl (data_only) reads `None`. Bit flecon, deliveries, production — each ships a local merge-aware `sheet.ts`. gsheet/rc_movement had no merges in load-bearing columns.
- **The migration process found live PYTHON bugs** (bug-for-bug parity is a feature): production classified **zero rows** for weeks (a `{"rows":…}` vs section-key wiring bug — fixed, recovered 2 days of data); the L-018 skip gap; a gsheet gate-crash; a `dt_mins≥60` DB-constraint crash. All handled with logged deviations (`PORTING_DECISIONS.md` + `expected-deviations.json`).
- **First real clicks exercise the SEAMS between proven pieces.** Each piece passed in isolation; the integration seams failed one-by-one on Renzo's clicks and were closed permanently: L-032 audit-write RPCs (INSERT *and* UPDATE need SECURITY DEFINER RPCs — service_role has no grant on `audit_logs`); the stuck queued-run (DBOS only recovers *started* workflows → added startup recovery + watchdog); Gmail silence (fetch was one opaque 2m40s step → per-report progress + attachment-only); the result-shape drift (worker flat envelope vs frontend nested `applied` + held rows).
- **DBOS TS specifics** (docs don't name them): cancel error classes are under the `Error` namespace (`import { Error as DBOSErrors }`); `getWorkflowStatus` returns PENDING/ENQUEUED/DELAYED live, CANCELLED after cancel; recovery only resumes STARTED workflows (hence the custom queued-run recovery).
- **The Write tool can inject control bytes** into adjacent `${…}` template literals (seen in gsheet + production ports) — `grep`/`Edit` then silently fail to match; detect with `grep -lP '[\x00-\x08…]'` and byte-fix via python.
