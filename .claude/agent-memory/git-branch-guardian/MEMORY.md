- **SHELL TRAP — `${PIPESTATUS[0]}` is silently EMPTY in this zsh environment** (bit me twice in one run, 2026-07-30: `VERIFY_EXIT=` and `ESLINT_EXIT=` both came back blank, which reads like a pass but proves nothing). zsh's array is `$pipestatus` (lowercase, **1-indexed**) — `${PIPESTATUS[0]}` is a bash-ism. **Fix: never pipe a gate command into `tail`/`grep` when you need its exit code.** Redirect to a log file, capture plain `$?`, then read the log: `cmd > /path/log 2>&1; echo "EXIT=$?"; cat /path/log`. An empty EXIT= is a FAILED verification, not a green one — re-run it. **Confirmed working 2026-08-03:** `git push … 2>&1 | tail -5; echo "PUSH_EXIT=${pipestatus[1]}"` printed a real `0` — the lowercase 1-indexed form IS reliable when you must keep the pipe.
- **Rename detection is a DISPLAY-time heuristic, not something the commit stores** — never promise "git recorded it as a rename" without checking `git diff --cached --stat` output. A moved file that is ALSO edited can drop below the 50% similarity floor and show as add+delete; that is cosmetic, the content is identical either way. Tiny files are the trap: a 5-line `page.tsx` whose import path changed + a comment header was added scored under 30% and never paired (2026-07-30 `app/(app)/production/page.tsx` → `(tabs)/page.tsx`), while its 3 unedited/lightly-edited siblings paired at 100%/65%. Test with `git diff --cached --stat -M30%` before reporting.
- **Route-group moves (`app/(app)/x/` → `app/(app)/x/(group)/`) need a route-table gate, not just a green build** — the URLs are supposed to be unchanged, and a silently-swallowed route still compiles. Grep the build log's emitted route manifest for the specific entries (2026-07-30: confirmed `ƒ /production` and `ƒ /production/schedule` listed as separate routes). Capture `npm run build` to a log file — the background-task output file only holds the echoed exit code, not the build's stdout.
- **"Files were deleted" in a task prompt often means UNTRACKED scratch that never entered git** — verify before reporting a deletion as staged. 2026-08-01 the brief said four draft files under `app/(app)/cenapro/analysis-drafts/` + `lib/cenapro/ccc-analysis-draft.ts` were "deleted" and told me to confirm they staged as deletions; they had only ever existed as `??` untracked files in the same session, so `git log --all -- <path>` was empty and `git diff --staged --diff-filter=D --name-only` was correctly empty. Nothing was wrong — but "no deletions staged" looks like a `git add` failure if you don't check. Two cheap proofs: `git log --all --oneline -- <path>` (empty = never tracked) and `git ls-tree -r HEAD --name-only | grep <path>`. Report it as "never tracked, nothing removed from history," not as a staging miss.

- **CORRECTION (verified 2026-07-11): `.gitignore` has ZERO `.claude`/`agent-memory` entries — nothing named `.claude` is actually gitignored in this repo.** The prior note below (any `agent-memory-local/` path being "GITIGNORED") was wrong; those paths just happen to never have been `git add`ed by anyone, not because a pattern excludes them. - (superseded detail, kept for the git-add-on-directory nuance) `git check-ignore` on a tracked file inside such a dir reports "not ignored" (tracked paths bypass the check) even when the dir looks gitignore-intended; `git add <dir>` still stages untracked files inside it since nothing actually ignores them. Never include `*/.claude/**` machine-local dirs in a shared commit — stage paths explicitly or unstage after a blanket `git add .`.
